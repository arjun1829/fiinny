## Fixed and deployed

### 1. Razorpay rejected ladder-priced checkouts — `c5c43ae7`

`app/api/payment/create-order/route.ts` sent `baseAmount * 100` as the paise
amount. For a decimal ladder price that is not an integer in floating point
(`10.15 * 100` is `1014.9999999999999`), and Razorpay rejects a fractional
amount, so those checkouts failed at order creation. Now rounded.

### 2. Refunds of paid-out orders failed, leaving the customer un-refunded — `f34cce9a`

A balance payout (`app/api/admin/payout-transfer/route.ts`) transfers the
seller's **net** — gross less gateway and platform fees — and a single transfer
can settle several of that seller's due orders at once, stamping the same
`transferId` on each.

`refundOrder` reversed the full **gross** of one order against that shared
transfer. Gross exceeds the order's net contribution whenever a gateway fee is
recorded, so Razorpay rejected the reversal; `refundOrder` deliberately returns
early rather than refund while the seller still holds the money, so the
customer got **no refund at all**. Where a transfer covered several orders, a
reversal could instead succeed and claw back funds belonging to the others.

Now reverses the order's own share, pro-rated for a partial refund. The payout
records `payment.transferredNet` per order so the reversal uses exactly what was
sent; `netFor()` recomputes it for orders transferred before that field existed.
`netFor` / `feesFor` are exported from `seller-earnings.ts` and used by both the
payout run and the reversal, so the two cannot drift apart.

### 3. Market page took 13–33s per page — `cac3b806`

The marketplace feed is identical for every visitor (distance ordering happens
in the browser), yet `app/api/marketplace/products/route.ts` sent
`Cache-Control: no-store`, so every request recomputed it. Emitting ~13 merged
cards costs up to 480 raw document reads across that many **sequential**
Firestore round-trips.

Added a bounded 60s module-scoped LRU plus
`public, s-maxage=60, stale-while-revalidate=300` so Firebase Hosting's CDN
serves repeats. Also removed a `debug` block that was shipping internal read
volumes to every client.

Measured: **13.3s to 0.12s** warm.

### 4. Search returned nothing for valid terms — `10f0438f`

Worse than slow — it was wrong. Firestore cannot do substring matching, so
search walked the name-ordered collection in bounded chunks and filtered in JS,
giving up after 1600 documents. Any term sorting late in the alphabet returned
an **empty page** while reporting `hasMore: true`.

Search now filters a full catalogue snapshot cached for 5 minutes, loaded
single-flight, with a 20k ceiling. Matches are found wherever they sort.

| query | before | after (warm) |
|---|---|---|
| urea | 0 products, 29.0s | 3 products, 0.69s |
| tractor | 0 products, 27.5s | 0 products, 0.10s |
| seed | 15, 41.9s | 18, 0.15s |
| bayer | 8, 28.6s | 9, 0.08s |

`tractor` returning 0 is now a correct answer (`hasMore: false`, whole
catalogue searched), not a timeout.

### 5. OpenAI Ads conversion tracking — `af893e7c`

Pixel installed site-wide; `subscription_created` reported for newly paid seller
plan enrolments. See "Pending" below — this is **not yet functional end to end.**

  Append `?oaiq_debug=1` to any URL for SDK console logging.

## Pending

### Blocking

- **`OPENAI_CONVERSIONS_API_KEY` is not set.** No server-to-server ad events
  can be sent. The endpoint returns `not_configured` and deliberately does not
  reserve the deduplication record, so nothing is permanently suppressed. Add it
  to `KrishiDukaan-V2/.env.local` **before** deploying — server env is bundled
  into the SSR function at deploy time, not read live.
- **Confirm the Pixel ID.** `WtoF4ur18Tyf8Z2ne9KxWP` was taken from the
  Conversions API snippet's `pid=` parameter, which the documentation defines as
  the Pixel ID. The Pixel setup snippet itself was never supplied. Worth
  confirming against Ads Manager.
- **Campaign linking is an Ads Manager step.** The campaign optimises for clicks
  and must be edited to use the "Subscription Created" conversion. No code
  change affects this.

### Known defects, not addressed

- **Successful payments do not reliably grant access.**
  `app/api/payment/verify/route.ts` only validates the signature; the **browser**
  writes the subscription afterwards. Close the tab at the wrong moment and the
  money is captured with no subscription created. 12 such payments exist with
  real `pay_*` ids, `status: success` and no matching subscription document.
  This is the single most consequential open issue in the payment flow.
- **Partial refunds can never be repeated.** `refundOrder` returns 409 on any
  second refund. Left as-is deliberately: allowing repeats needs cumulative
  refunded-amount tracking first, or it risks over-refunding.
- **`resetTenantUserPassword` is not deployed** on the KaranArjun ERP, while
  `firebase.json` rewrites `/api/users/reset-password` to it. Password reset is
  dead in production there.

### Performance, mitigated but not fixed

- **First request after idle is still slow** — ~19s for a cold search, ~13.7s
  for cold browse, because that request rebuilds the cache. Steady traffic hides
  it; a quiet period does not.
- **Category browse is ~12s cold.** Still reads Firestore in chunks; left
  untouched because it has no correctness bug.
- **Root cause remains.** Roughly 32 duplicate copies exist per product and are
  merged at read time. A canonical one-doc-per-name collection, maintained by a
  Cloud Function on product write, would make a page read ~20 documents instead
  of 480 and remove the cold-start cost. This is the real fix.
- **Cold start on the SSR function** adds ~30s to a first hit. `minInstances`
  would remove it at the cost of an always-warm instance — a spend decision.

### Coverage gaps

- **Mobile subscriptions are not tracked.** The Flutter app has its own
  subscription purchase and Razorpay checkout; the web pixel never runs there,
  so those enrolments will not appear as conversions.
- **The ads conversion path is unproven.** No real payment was put through. The
  renewal and deduplication branches are typechecked and reasoned but not
  exercised against live data or an emulator.
- **`next.config.js` sets `typescript.ignoreBuildErrors` and
  `eslint.ignoreDuringBuilds` to true**, so a green `next build` proves nothing
  about type safety. Typechecking must be run separately.
